## 1. Цель работы

Отработка практических навыков интеграции клиентского одностраничного веб-приложения с серверным REST API по протоколу HTTP: реализация асинхронного HTTP-клиента на базе Fetch API с корректной обработкой статусов ответов (включая 204 No Content, ошибки 4xx/5xx и таймауты с AbortController), валидация данных форм на клиенте и сервере, реализация состояний интерфейса (loading, ready, empty, error), выполнение CRUD-операций с задачами (создание, чтение, редактирование, изменение статуса, удаление) и предотвращение состояния гонки (race conditions) при смене фильтров.

## 3. Реализация

### 3.1. HTTP-клиент

Модуль `src/api-client.js` реализует фабрику `createApiClient`. Поддерживаются HTTP-методы `GET`, `POST`, `PATCH`, `DELETE`.
- При наличии тела запроса объект сериализуется в JSON и выставляется заголовок `Content-Type: application/json`.
- Для всех запросов выставляется заголовок `Accept: application/json`.
- Для успешных ответов со статусом 204 (No Content) возвращается значение `null` без вызова `response.json()`.
- При получении кодов ошибок 4xx/5xx клиент извлекает тело ошибки и выбрасывает специализированное исключение `ApiError` с полями `kind: "http"`, `status` и деталями ответа.
- Таймаут запросов реализован через `AbortSignal.timeout(timeoutMs)` с поддержкой объединения через `AbortSignal.any` с внешним сигналом отмены пользователя, позволяя точно отличать таймаут (`kind: "timeout"`) от отмены (`kind: "aborted"`).

### 3.2. Доменный API

Модуль `src/task-api.js` (`createTaskApi`) реализует абстракцию операций над задачами:
- `getTasks(filters)` — получение списка с нормализацией параметров поиска и фильтрации;
- `getTaskById(id)` — чтение задачи по идентификатору;
- `createTask(draft)` — отправка POST-запроса на создание задачи;
- `updateTask(id, patch)` — частичное обновление задачи через PATCH;
- `setTaskCompleted(id, completed)` — изменение статуса выполнения задачи;
- `deleteTask(id)` — удаление задачи (DELETE, 204);
- `getCategories()` — получение справочника категорий;
- `loadInitialData(filters)` — параллельная загрузка задач и категорий через `Promise.all`;
- `resetDemoData()` — сброс данных API к исходному состоянию.

### 3.3. Состояния интерфейса

В контроллере приложения `src/app-controller.js` реализованы 4 взаимоисключающих состояния UI:
- `loading`: показывается индикатор загрузки, скрываются карточки, сообщения об ошибках и пустоте;
- `ready`: отображается список карточек задач при наличии элементов;
- `empty`: активируется при успешном ответе сервера с пустым массивом задач (`tasks.length === 0`), список очищается и показывается сообщение об отсутствии задач;
- `error`: показывается блок с сообщением об ошибке и кнопка повтора запроса.

При повторной загрузке состояние переходит в `loading`. Ошибки отмены (`aborted`) от предыдущих устаревших запросов перехватываются и не приводят к показу экрана ошибки.

### 3.4. Изменение данных

- **Создание:** данные формы проходят валидацию функцией `validateTaskDraft`. При успехе элементы управления формы блокируются, отправляется `POST /api/tasks`, форма очищается, и список задач перезапрашивается с сервера для синхронизации с текущими фильтрами.
- **Редактирование:** клик по кнопке редактирования переводит форму в режим правки с заполнением полей выбранной задачи. При отправке выполняется `PATCH /api/tasks/:id` и повторный запрос списка.
- **Смена статуса:** клик по кнопке выполнения задачи отправляет `PATCH /api/tasks/:id` со значением `{ completed: !currentStatus }` и перезапрашивает список.
- **Удаление:** клик по кнопке удаления отправляет `DELETE /api/tasks/:id` (204 No Content), после чего список обновляется.

### 3.5. Защита от устаревшего ответа

Для защиты от состояния гонки (race conditions) при быстрой смене фильтров и повторных запросах:
1. При каждом новом запросе списка вызывается `abort()` у предыдущего активного экземпляра `AbortController`.
2. Ведется счетчик текущей загрузки (`loadSeq`). Если завершившийся асинхронный запрос имеет устаревший токен, его результат игнорируется и не обновляет интерфейс.
